# The phone app and working offline

*English · [Lietuviškai](lt/pwa.md)*

Logify is a Progressive Web App (PWA): it can be put on a phone's home screen, opens full-screen like an app, and works without signal. You can see your plans, history and progress (instructors: their athletes) and log a workout. The workout waits on the phone and is sent, with the instructor's email, when the signal returns.

This page explains how the offline parts work, how to test them, and where the limits are. For the user's point of view see the [athlete manual](user-manual/en/athlete.md#10-using-logify-without-signal); for the layers of the code see [architecture.md](architecture.md#6-the-offline-layer), and for the parts and the network edges the component diagram in [Mobile architecture (PWA)](architecture.md#7-mobile-architecture-pwa). Which module does what is in [section 10](#10-where-this-lives-in-the-code). The design and the plan it was built from are in [the design](superpowers/specs/2026-11-16-pwa-offline-design.md) (see its *As built* section for what changed during the build) and [the plan](superpowers/plans/2026-11-16-pwa-offline.md).

## 1. The installable app

| Piece | What it is | Where |
|---|---|---|
| Service worker | Keeps the app's own files on the phone, so every screen opens with no network. Generated by [vite-plugin-pwa](https://vite-pwa-org.netlify.app/) (Workbox, `generateSW`) at build time | `vite.config.js` → `dist/sw.js` |
| Manifest | Name and short name *Logify*, `display: standalone`, portrait, theme color `#0f766e`, background `#f5f6f8`, start page `/`. Two home-screen shortcuts on Android (long-press the icon): *Įrašyti treniruotę* → `/log` and *Pažanga* → `/progress`. Its texts are in Lithuanian, because a manifest can't follow the language switch | `vite.config.js` → `dist/manifest.webmanifest` |
| Icons | 64, 192 and 512 px, a 512 px maskable icon and a 180 px Apple touch icon, all made from `public/favicon.svg` and committed | `public/*.png` |
| Page tags | Apple touch icon, the iPhone home-screen title, and `viewport-fit=cover` so the app fills the screen around the notch. The manifest link carries `crossorigin="use-credentials"`, so a Vercel preview's password protection can't block it | `index.html` |
| Install card | On **My plans**: Android and Chrome get *Install* (the browser's own install offer), iPhone Safari gets the Share → Add to Home Screen steps. Hidden once the app is installed, and for good after *Not now* / *Got it* | `src/components/InstallCard.jsx`, `src/pwa/installPrompt.js` |

The service worker caches the built app only: the HTML, every JavaScript chunk (including the ones loaded on demand, such as Progress), the CSS and the images. It serves `index.html` for any address, so a route such as `/progress` opens offline too. It does **not** touch requests to Supabase (they go to another origin and are not routed); the data comes from the saved data below.

`npm run dev` runs without a service worker, so a stale cache never confuses development. Use `npm run build` and `npm run preview` to see it (section 7).

### Updates

A new version is downloaded in the background and then waits. A line under the header says *A new version of Logify is ready.* with **Update**; the app never reloads by itself, so a half-filled workout is never wiped. An open app asks for a new version every hour (`UPDATE_CHECK_MS` in `src/pwa/serviceWorker.js`); a check that fails (offline) is simply made again the next hour. Pressing **Update** reloads the page into the new version; the unsaved workout comes back from the draft (section 4). While a workout is being sent, the line waits, because the reload would cut the send off. The very first service worker takes over the open page at once (`clientsClaim`), so the first session after installing already works offline; later versions still wait for **Update**.

### The header and the tab bar

On phones the header is one row: the logo, the language switch and the account.

- **The language switch is two small flags**, Lithuanian and British, right next to the logo. Underneath they are radio buttons, so the keyboard works and a screen reader reads each language's name in that language: *Lietuvių* and *English*.
- **Log out is an icon** (a door with an arrow). Its name is *Log out* and its tooltip reads *Log out (the user's email)*. The email next to it is cut with … when there is no room, so it never runs into the flags (checked from 320 to 1024 px).
- **At 640 px and below the menu is a bar fixed to the bottom of the screen**: **My plans**, **Log**, **Progress**, and **Sharing** (athletes) or **My athletes** (instructors). **Log** exists only on phones. The header and the bar keep clear of the notch and the home indicator.

`src/components/Layout.jsx`, `src/components/LanguageSwitcher.jsx`, `src/components/NavIcons.jsx`, `src/index.css`.

## 2. What is kept on the phone, and where

Everything below is per user where it says so, so two people sharing one phone never see each other's data.

| What | Where | Notes |
|---|---|---|
| The app's files | Cache Storage (service worker) | Replaced when a new version is installed |
| Saved data | `localStorage` · `logify.cache.v1.<user id>.<key>` | The last data each screen loaded, with the time. Keys: `plans`, `planOptions`, `progress`, `workout:<id>`, `instructors`, `athletes`, `athlete:<id>`, `report` |
| Workouts waiting to send | `localStorage` · `logify.outbox.v1.<user id>` | See section 4 |
| The unsaved Log workout form | `localStorage` · `logify.draft.v1.<user id>` | One per user |
| The database's version | `localStorage` · `logify.dbVersion` | The last answer of `schema_version()`, so it is known offline |
| The install card was dismissed | `localStorage` · `logify.installCard.dismissed` | |
| The older-database warning was hidden | `sessionStorage` · `logify.oldDbWarning.hidden` | For the rest of the session only |
| The sign-in | `localStorage` · `sb-…-auth-token` | Kept by supabase-js; Logify only reads it |
| The language | `localStorage` · `logify.language` | |

Limits of the saved data:

- At most **30** saved `workout:*` entries and **30** saved `athlete:*` entries per user (the ones opened last); the oldest are dropped first.
- If the phone's storage is full, that user's oldest saved data is dropped until the new entry fits. Workouts waiting to send, and the draft, are never dropped to make room for saved data.
- On **log out**, that user's saved data and draft are deleted from the phone. Workouts waiting to send stay (section 4).

## 3. Showing saved data

Every screen that reads data (`useLoad` in `src/lib/useLoad.js`) tries the network first and saves what it got.

| Situation | What the screen shows |
|---|---|
| Online and fast | The fresh data. It is saved for next time |
| The phone says it is offline | The saved data straight away |
| The network fails (no signal, dropped) or is slower than **4 seconds** | The saved data, with the line *Offline: showing data saved on {time}.* and **Try again**. If the fresh data arrives later, it replaces the saved data |
| Back online while saved data is shown | The screen loads again by itself and swaps in the fresh data (no Loading flash) |
| A real error (for example no permission) | The Error state, as always |
| Offline and nothing saved yet | The Error state: *You're offline, and this hasn't been saved on this phone yet.* |

**A load never undoes a local change.** A rename, a delete or a workout that has just been sent changes the data on screen. A load that started before such a change can't contain it, so when its answer (data or error) arrives it is dropped and the load runs again, with the current data kept on screen (no *Loading*, no *Error*). Only an answer from a load that started after the last change is shown and saved. (`Try again` still shows *Loading*.)

**A local change always reaches the saved copy, without making it look newer.** The change is written to the saved copy even while saved data is shown, so a slow reconnect or a failed re-run can't bring back a copy without it. While saved data is shown, the copy keeps its own *saved on* time; fresh data is saved as of now.

**Warm-up.** Right after sign-in, or on app start with a connection, the app quietly loads the plan options and Progress (instructors: My athletes too) and saves them, so offline works for screens you haven't opened yet. `src/offline/warmUp.js`.

**My plans and the Log workout plan list stay in step.** Whenever My plans saves its plans (a fresh load, a rename, a delete), the Log workout screen's plan list is saved from them too, unless that list was saved more recently. Every workout the server takes is added under its plan to the saved copy of My plans, even when My plans isn't open. So offline the Log workout screen offers a plan created since the warm-up, and My plans lists a workout sent from the Log workout screen. `src/offline/plansCache.js`.

**Hints while logging.** When the phone says it is offline, the exercise-name suggestions and *Last time* come from the saved Progress data at once, without a request that would have to fail first (supabase-js would retry for about 7 seconds). They also fall back to it when a request fails for lack of network. `src/offline/hints.js`.

**No data request without a sign-in.** After a long offline period the access token has expired. Until supabase-js has a usable session again (after reconnecting it can wait up to a minute before it refreshes), it would send database requests with only the project key, and Row Level Security would answer with empty lists, which a screen would save over good data. `src/lib/sessionGuard.js` makes such a request fail like a dropped connection instead, so screens keep their saved data and the outbox waits. The database version check (`schema_version()`) is the one exception: anyone may call it and it only returns a constant, so it goes out at once and the version is known as soon as the connection returns.

### Staying signed in offline

supabase-js keeps the session in `localStorage` and deletes it only when the server rejects it. Offline, with an expired access token, it can't refresh and reports "no session" although the session is still stored. `AuthProvider` handles that case: when Supabase reports no session at start but a complete stored one exists, it uses the stored one, so you stay signed in on this phone (`src/auth/AuthProvider.jsx`, `src/auth/storedSession.js`). It doesn't wait for that report either: with an expired access token supabase-js reports the session only once its refresh retries give up (about 25 s with no signal), so a complete stored session is used at once when the phone is offline, and after 3 seconds on a slow connection; whatever Supabase reports later decides. When the connection returns, supabase-js refreshes the token by itself; if the server rejects it, you are signed out and sent to Login, as before. **Logging in** (and signing up) needs a connection, and the Login screen says so offline.

**Log out offline** signs out on this phone only, because the server can't be reached; the server session just expires. Online, it signs out everywhere, as before.

## 4. Logging a workout offline: the outbox

The outbox is `src/offline/outbox.js` (what is kept) and `src/offline/sync.js` (what is sent).

1. When you press **Save workout**, the phone makes an id for the workout (a UUID) and notes the time. The workout is written to the outbox first, then sent.
2. **Online:** it is sent at once, waiting at most **15 seconds**. If the server has it, you see *Workout saved*, as before.
3. **Offline, no answer, or no answer within 15 seconds:** the form says *Saved on this phone. It will be sent as soon as there's a connection, and your instructor gets the email then.* and clears. The workout shows as **Waiting to send** under its plan on **My plans**.
4. **Any other error** (for example the plan was deleted, or the instructor stopped assigning it): the workout is not kept, and the form shows the error so it can be fixed.
5. **If the phone's storage is full:** saved data is dropped to make room. If the workout still can't be kept on the phone, then **online** it is sent directly, the way it was before the outbox (without the phone's id, so it isn't protected against a second copy after a dropped connection), and you see *Workout saved* as usual; only **offline** does the form say it couldn't be kept, and it never says it was saved.

**While Save is working** (up to the 15 seconds), the form's fields are locked and the button says *Saving…*. The form clears when the workout is saved or kept, so anything typed meanwhile would be lost without a word.

**Sending.** Waiting workouts are sent oldest first, one at a time, while the app is open: when the app starts, when the connection returns, when the app comes back into view, right after a successful save, every **30 seconds** while something waits, and on **Send now** in the status line. Before each send it checks that Supabase holds *this user's own* session; if not, it waits.

| Outcome | What happens |
|---|---|
| Sent | The workout leaves the outbox and becomes a normal row |
| No response, the time limit, an HTTP 5xx, an expired or rejected sign-in (401), or a duplicate id (`23505`) | **Try again later**: it stays *Waiting to send* and the round ends |
| Any other error | **Couldn't send: {reason}** with **Try again** and **Delete** (which asks first), on **My plans**; the round goes on with the next workout |

If the workout's plan is no longer in the list (deleted or unassigned), it shows in a **Workouts waiting to send** card at the top of My plans instead. A waiting row is not a link: it has no page until it is sent. Progress, suggestions and reports count only workouts the server has.

**Log out with workouts to send** asks first: they stay on this phone and are sent the next time that user logs in here. The question counts only the workouts that will be sent by themselves (*Waiting to send*, or being sent). One that *Couldn't send* is never sent automatically, so on its own it doesn't make Log out ask: it stays on **My plans** for **Try again** or **Delete**, after a log out too. If the last workout is sent while the question is open, the question closes by itself. Another user who logs in on the same phone neither sees nor sends the workouts.

**The unsaved form.** The Log workout form is saved on the phone as you type, so an app restart, an update, or the phone closing the app in the background doesn't lose it. A restored form says *Unsaved workout restored.* with **Start over**. If the form is opened from a plan's **+ Log workout**, that plan wins over the plan in the draft. It is cleared on log out, and in the cases below.

- **The moment the outbox holds the workout**, not when the send settles up to 15 seconds later. Otherwise closing the app in between would send the workout from the outbox *and* restore the form, and a second Save would make a second workout and a second email. While the form is saving, nothing is written to the draft either, so a late blur in a field can't bring it back.
- **Not cleared if the workout isn't kept after all:** if the server refuses it, or the phone can't keep it, the form keeps its fields and writes them as the draft again.
- **Not cleared early when the phone is full** and the workout is sent directly (there is no copy in the outbox): the draft stays until the server answers.

### Exactly once

A workout must never be saved twice, and the instructor must never be emailed twice, however many times a send is repeated (the phone may never see the server's answer). So:

- the app sends the id made on the phone as `p_id`, and the time Save was pressed as `p_logged_at`, to `log_workout()`;
- if that user already has a workout with that id, the function returns it and inserts nothing: no second row, no second webhook, no second email;
- if two sends race, the second hits the primary key (`23505`); the app tries again later and the function then finds and returns the workout. The app never assumes a workout was saved unless the server returned it;
- `p_logged_at` becomes the workout's `created_at` if it is within the last **30 days** and not in the future; otherwise the server's time is used. So a workout sent hours later still lands on the right day in the charts and *Last time*.

The database side is in [supabase.md](supabase.md#6-offline-logging-v5); the whole path is drawn in [architecture.md](architecture.md#6-the-offline-layer).

## 5. The older-database warning

The app works with a database from before v5 too (so the same build can run against a project where `supabase/schema.sql` hasn't been re-run). The database tells its version: the function `schema_version()` returns `5`, and the app asks once per start while online and remembers the answer (`src/offline/dbVersion.js`, `src/api/schema.js`). "Function not found" means older than v5; no answer (offline) keeps the last known value.

If `log_workout()` answers "function not found" to the new parameters (a database that was rolled back, or PostgREST's schema cache not yet reloaded), the app marks the database as older and repeats that send the old way at once.

On an older database everything works, including logging offline, with two differences:

- the send leaves out `p_id` and `p_logged_at`, so a workout logged offline gets the time it is **sent**;
- a send is never cut off by the 15 second limit (the form still stops waiting after 15 seconds and says the workout is kept on the phone), because cutting it off could leave a saved workout looking unsaved. Only a connection that really drops mid-send can then cause a second copy.

The status line under the header says so, with **Hide** for the rest of the session:

> Logify's database is an older version than this app: workouts logged offline get the time they're sent, and after a dropped connection one could be saved twice. The fix is updating the database (supabase/schema.sql).

It disappears by itself once the database reports version 5. To fix it, run `supabase/schema.sql` again ([supabase.md](supabase.md#applying-v5-to-an-existing-project)).

One line under the header, shown only when there is something to say (`src/components/StatusBar.jsx`):

| Line | When |
|---|---|
| *A new version of Logify is ready.* **Update** | A new version has downloaded, and no workout is being sent |
| *You're offline. Workouts you log are kept on this phone.* | No connection |
| *Sending…* | A workout is being sent |

## 7. Testing it offline

A service worker needs HTTPS or `localhost`, and it is not active under `npm run dev`. Test the production build:

```bash
npm run build
npm run preview        # http://localhost:4173
```

1. Open the preview in Chrome and log in **while online**. This installs the service worker and runs the warm-up. (DevTools → Application → Service Workers should show it as *activated*; Application → Manifest shows the manifest and icons.)
2. Open My plans, Log workout and Progress once, so there is saved data to fall back on.
3. DevTools → **Network** → set throttling to **Offline** (or stop the preview server and reload).
4. Reload. The app opens. The status line says *You're offline…*, and screens show *Offline: showing data saved on …*.
5. Log a workout. The form says it was saved on the phone, and **My plans** shows it as *Waiting to send*.
6. Set throttling back to **No throttling**. Within a moment (or on **Send now**) the status line clears, and the workout becomes a normal row.

The unit tests need none of this: they never use the network (the real `supabase-js` client runs against a fake `fetch`, `src/test/fakeBackend.js`).

To try it on a real phone, open a Vercel preview or the live site over HTTPS. If the preview shows "The app is not set up yet", the two Supabase variables aren't enabled for Vercel's Preview environment ([deployment.md](deployment.md)).

## 8. Regenerating the icons

The icons are made from `public/favicon.svg` and the PNGs are committed, so the build needs no image tools. When the logo changes, run this once and commit the new files:

```bash
npx --yes @vite-pwa/assets-generator@2.0.0 --config pwa-assets.config.js
```

The version is pinned and the generator is not a dependency of the project. `pwa-assets.config.js` says what to make: 64, 192 and 512 px transparent icons, a 512 px maskable icon and a 180 px Apple touch icon. The last two have padding in `#0f172a`, the icon's own edge color, so the padding can't be seen.

## 9. Limits

| Limit | Why |
|---|---|
| **No background sync.** A workout is sent only while the app is open (or in view) | iPhone doesn't support Background Sync, and on Android it would need the session inside the service worker |
| **Only logging works offline.** New, edited or deleted plans, workout renames, goals, reports, sharing and plan assignment need a connection and show *Can't reach the server…* | Each would need its own conflict rules; the scope is "view + log" |
| **iPhone: the installed app has its own storage.** Logging in in Safari doesn't log you in inside the home-screen app: log in once more there. Its saved data and waiting workouts are separate from Safari's | iOS gives a home-screen app its own storage, apart from the Safari tab |
| **iPhone: Safari may clear a website's storage** after a period without use. The installed home-screen app is not affected by that rule | A browser rule, out of the app's hands; this is one more reason to install it, and not to leave workouts waiting for weeks |
| **The logged time counts only for 30 days.** A workout older than that, or with a time in the future, is saved with the time it is sent | The database ignores an implausible `p_logged_at` |
| **Supabase's one-minute pause.** If the sign-in expired while offline, after a failed refresh supabase-js waits up to a minute before trying again, so things resume within about a minute of reconnecting | A supabase-js behaviour |
| **Saved data is a copy.** It is as old as the last time that screen loaded; the line says when. Only the 30 most recently opened workouts and athletes are kept | Phone storage is small |
| **Browser minimums:** Chrome 111, Safari 16.4, Firefox 121 | `crypto.randomUUID`, `AbortSignal.timeout` and service workers |
